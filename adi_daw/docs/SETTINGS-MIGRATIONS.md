# Settings schema steps (PD-11)

The production schema is still **1** and the production migration table is empty. This change invents no historical settings transformation and does not alter any setting default. Schema-less legacy documents are the first published format, schema 1.

`settings/migration.hpp` provides a pure document runner with an injected list of adjacent `from -> from + 1` steps. Each callback edits only the `values` object; the runner owns schema advancement, retaining application identity and other top-level fields. The complete route and unique registrations are checked before running any callback. Missing, ambiguous, non-adjacent, null or oversized step lists fail explicitly. Callback refusal, exceptions, or a non-object result return no partial document and never mutate the input. A future step must define its own rename-collision and invalid-value policy; the runner does not replace user values with defaults.

The same runner is used at load and on the existing pre-save reread. Loading performs transformations in memory only. Saving rereads and migrates the latest on-disk document before overlaying this instance's pending edits; the existing atomic publisher and concurrent-writer checks are unchanged. The `.bak` contains the original on-disk bytes, not an already-migrated reconstruction. A failed save retains pending keys for a later retry.

Newer schemas retain their existing read-only behavior, even when their remaining shape is unfamiliar. Another application's file is untouched. A syntactically malformed current document follows the existing corrupt-file preservation behavior. A well-formed older document with no supported migration route, or a failed registered transformation, stays at its original path with `LoadStatus::MigrationFailed` and an explanatory `migrationError()`. That instance refuses writes even if the original subsequently disappears. Schema 0 therefore cannot be silently relabelled as schema 1 without an explicitly registered transformation.

`adi_settings_migration_tests` exercises a synthetic 1 -> 2 -> 3 rename/default sequence with the user's value retained, route preflight, callback failure atomicity, malformed/newer/foreign inputs, and the real settings store's reread and exact-backup protections. Those synthetic steps are test-only; they are not shipped as production migrations. Debounce, retry scheduling and shutdown flush belong to the separate PD-11 scheduler slice.
