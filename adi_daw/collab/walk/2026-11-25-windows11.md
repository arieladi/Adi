# Walk A — the one session, in the real window, on Windows 11 (25 November 2026)

Walker: walk-A, a helper of win, by the director's order of 25 November 2026.
The session walked is ADR-0248 decision 2 (adi_daw/docs/DECISIONS.md), owed by 3 December.
Sister report: walk-B on branch `walk/windows10`, same folder.

## The machine

- OS: Windows 11 IoT Enterprise LTSC 2024 (10.0.26100), 16 logical cores.
- Audio: one output only, an HDMI display's audio (NVIDIA HD Audio, WASAPI). **No audio input of any kind**
  (the onboard codec exposes no capture endpoint; no microphone, no line-in).
- At first there was no virtual audio cable or virtual MIDI port, and the walk runs without administrator rights.
  After pass 1 the director installed a virtual audio cable (VB-Audio Virtual Cable, with Voicemeeter) and loopMIDI,
  and the machine was restarted. From pass 1b on: ADI records from the cable's "CABLE Output", into which a script
  plays a test signal, and plays notes it receives on a loopMIDI port, into which a script sends notes through WinMM
  as a keyboard would.
- VST3 instruments installed: several third-party ones; the walk used an open-source synth.
- Build: origin/main at 73e26e4aa, RelWithDebInfo (optimised, with symbols), Ninja, MSVC 2022,
  `-DADI_WITH_JUCE=ON -DADI_WITH_PD=ON -DADI_WERROR=ON -DADI_ACCEPTANCE=ON`; targets `adi_app` and `adi_plugin_scanner`.
- ADI started with `ADI_HOME` set to a new empty folder; projects saved to a scratch folder outside the repo.
- Driven with: synthetic input from scripts (Win32 `SendInput`, with real scan codes, mouse moves in small steps
  for drags), and screenshots of ADI's own windows after every action. The session's computer-use tools could not
  be granted an application that is not installed through the Start menu, so the brief's fallback was used.
- Heard with: a WASAPI loopback capture of the output device ADI plays to, analysed by level and by frequency
  band (the test material has known tones and clicks). The system volume was kept at 8 % at night, so every
  capture sits about 38 dB under the file's level.

## For the director

1. **No way to play notes without hardware.** Step 3 says "plays a keyboard". ADI's Computer MIDI Keyboard (Live's M) is a placeholder ("not built yet"), with no on-screen keyboard and no audition from the piano roll. A user with no MIDI keyboard cannot play OneShot or a plug-in live at all. It is planned in the key-map row of PLAN.md, but it is new work under ADR-0248's "fix before new", so walk-A did not build it. Is it in or out of the session owed by 3 December?
2. **Neither walk machine has an audio input.** This Windows 11 machine has none, and walk-B's report says the same of its Windows 10 machine (the jacks are unplugged; no capture device). Recording a take in the real window (step 2) is therefore proven only headlessly. It needs a machine with an input, or a virtual audio cable, which needs an administrator to install a driver. Separately, ADI's own "Loopback input" setting (`audio.loopbackSource`, ADR-0106) has no reader, so ADI cannot record its own output either.
3. **Recording automation by moving a control** (Live's Automation Arm + Arrangement Record) is not wired: `ProjectDocument::setAutomationArmed` always passes "not recording" (per the code map; it could not be walked here because F9 refuses with no input). Step 7 was walked by drawing breakpoints, which works. Is recorded automation part of the 3 December session?
4. **OneShot is not in the Browser** (A7): Instruments is empty until "the devices lane's instruments and MIDI effects" land. The only way to OneShot is a picker on a Mix View Stack row. walk-A left this to its owner, as it is a Browser feature rather than a fault in a path that exists.

## What this machine could not check
